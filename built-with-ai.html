Field Report — How This Site Is Built

AI builds this site. A person approves every page change.

Parallel AI builders work in isolated branches, an independent AI reviewer checks what they made, and no page change publishes until I say so. Here is the loop, the public record behind it, and a small gate you can try yourself.

Try the gate ↓

First published: 2026-10-19. Pull-request details and counts below were read from GitHub on 2026-10-19.

How is this site built?

By AI agents working under a written plan, each on its own Git branch, followed by an independent AI reviewer and then a human decision. The builders write the pages. A separate reviewer looks for what is wrong with them. I read the result and decide whether it merges. This site is hosted on GitHub Pages, so a merge to main is also a publish. For any change to a page, the merge is the control point, and it is mine.

The loop

The same cycle runs for every batch of changes. The AI does the volume work; the steps that carry authority stay with a person.

  1. Plan. A written batch plan names the lanes and the files each lane may touch, so parallel work can't collide.
  2. Build in parallel. Each lane is an AI builder on its own branch. Branch names in the repository follow the work, such as pub/authorizations-record and pub/deck-fixes.
  3. Independent review. A separate AI reviewer, not the one that wrote the change, reads it and reports what's wrong.
  4. Fix rounds, at most two. Findings go back to the lane. If two rounds don't settle it, the question comes to me instead of looping.
  5. Human nod. I decide whether any change to a page merges: copy, content and visuals are mine to approve. Internal docs can merge without it.
  6. Merge is publish; then check the live page. Pushing to main is the deploy, so the check that matters is on the page a visitor sees.

What keeps the agents honest

Four mechanisms do most of the work. The method itself lives in private notes, because the site's repository is public. This is what each one does.

  • A written batch plan. Scope is decided before anyone writes, and each lane's allowed files are listed.
  • A facts file every public claim must trace to. Statements about my career have to match a private, source-checked facts file. Statements about the tooling have to match the field reports linked below.
  • A do-not-write list. Claims I've ruled out because they don't hold up are listed, and reviewers check drafts against the list.
  • One writer for shared state. Shared records have a single writer, so parallel lanes can't overwrite each other. The failures this prevents are documented in what breaks when two AI agents share a notepad.

Simulation

Try a fail-closed gate

The loop above relies on one idea from my plan-gate field report: don't ask an agent to behave; put a check it doesn't control between its intent and its effect, and let that check default to deny. Propose an action below and see what a gate like that does.

A simplified illustration. This is a small script running in your browser, written to follow how the field reports describe the gate. It is not the StrictLock code, and nothing here touches a real system or a real log. It also leaves out the real gate's two deliberate exceptions: it fails open if it crashes, and a person can switch it off with an emergency bypass.

The approved plan in this simulation
  • Files that may be written, exact paths: plan-gate.html
  • Commands that may run, approved prefixes: git status, git diff, git add, git commit
  • The gate's own log directory: gate-logs/

In the described gate, HELD and BLOCKED are both denials. The demo separates them to show the difference between "outside the plan, a person could widen it" and "no plan can authorize this". The log line carries a timestamp, the decision, a class, the target, the previous line's hash and its own. The real log chains SHA-256 hashes; this simulation uses a short non-cryptographic hash so it fits on one line. The honest boundary from the field report applies: the chain makes edits and deletions inside the record detectable, but cutting off the last line goes unnoticed without an external anchor. Try "Delete the last line" to see it.

What this page does not claim

  • The demo above is an illustration, not the code that gated these pull requests.
  • An AI reviewer is one layer, not a guarantee. The review rounds in the pull requests caught problems; they don't promise there were none left.
  • The human nod is a person reading and deciding. It is not a gate, and it only works as well as the reading.
